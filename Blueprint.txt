OPEN PLATE — IMPLEMENTATION BLUEPRINT

Scope:
Implement only the functionality explicitly specified in the Open Plate PR. Do not add improvements, additional endpoints, authentication, deployment features, database alternatives, or other functionality not stated in the specification.


1. OBJECTIVE

Build a Universal File Naming API that:

Raw file name
        ↓
Tokenization / normalization
        ↓
Standardized machine-readable name
        ↓
Persist record in SQLite
        ↓
Return UUID + generated name

Example:

Input:
google chrome passwords.csv

Output:
dapa_gogl_chrm_pswd_usen_6811.csv


2. REQUIRED NAME FORMAT

The generated filename must follow:

<platform>_<place>_<persona>_<purpose>[_extras...]_<language>_<date>.<ext>

The generated name must therefore contain:

- Platform
- Place
- Persona
- Purpose
- Optional extra segments when required
- Language
- Date
- File extension


3. NAME PARSING

File:

src/nameParser.ts

Responsibilities:

- Accept the raw filename information.
- Tokenize the raw name.
- Remove stop words.
- Convert relevant words into 4-letter codes.
- Apply the specified consonant-reduction fallback.
- Apply the specified brand/name overrides.

Required overrides include:

google → gogl
chrome → chrm
passwords → pswd

The parser must produce the segments required by the standardized filename format.

Do not introduce additional naming rules beyond those specified by the PR.


4. PLATFORM

File:

src/plateService.ts

Responsibilities:

- Use "dapa" as the default platform prefix.
- Support the PLATFORM environment variable as an override.

Default:

dapa

If PLATFORM is configured, the configured platform value is used instead.


5. DATE GENERATION

File:

src/plateService.ts

Responsibilities:

- Generate the date component according to the specification.
- Derive the date code from YYMMDD.
- Apply the specified zero-stripping rule.

Required example:

2026-08-11 → 6811

Do not create a different date-formatting scheme.


6. FILE EXTENSION

The generated filename must preserve/use the appropriate file extension.

The implementation must support the specified NAKF fallback behavior.

If the extension cannot be determined according to the specified behavior, use:

NAKF

The NAKF extension fallback must be covered by the required tests.


7. PLATE SERVICE

File:

src/plateService.ts

Responsibilities:

- Receive the parsed filename information.
- Assemble the standardized filename.
- Apply the platform.
- Apply the language code.
- Apply the generated date code.
- Apply the file extension.
- Produce the final generated filename.

Example result:

dapa_gogl_chrm_pswd_usen_6811.csv


8. DATABASE

File:

src/db.ts

Database technology:

SQLite

Library:

better-sqlite3

Requirements:

- File-based SQLite database.
- Zero-configuration database setup.
- Persist generated plate records.
- Store the UUID associated with the generated record.
- Store the generated filename information required for retrieval.

No PostgreSQL, MySQL, Redis, or other database technology is required.


9. CREATE API

Endpoint:

POST /api/v1/plate

Purpose:

Generate and persist a standardized filename.

Flow:

1. Receive the raw filename request.
2. Parse/tokenize the filename.
3. Generate the required filename segments.
4. Generate the date component.
5. Determine the file extension.
6. Apply NAKF when required.
7. Assemble the standardized filename.
8. Generate a UUID.
9. Persist the plate record in SQLite.
10. Return the UUID and generated filename.

Required response structure:

{
  "id": "<uuid>",
  "generatedName": "<standardized filename>"
}


10. READ API

Endpoint:

GET /api/v1/plate/:id

Purpose:

Retrieve a stored plate record by UUID.

Flow:

1. Receive the UUID from the URL.
2. Look up the corresponding record in SQLite.
3. Return the stored plate record.

The implementation only needs the read operation specified by the PR.

Do not add update or delete functionality.
